# 11 · 将 RapidOCR 改写为本项目自有代码 —— 设计方案

| 项 | 内容 |
| --- | --- |
| 动机 | 把 OCR 从"第三方依赖"变为"本项目的一部分",消除外部依赖的维护/合规/升级耦合 |
| 现状 | `thirdparty/rapid-ocr-rs`(vendor)+ `thirdparty/snow-memory`,Apache-2.0 |
| 性质 | **设计方案,未修改代码** |
| 关键前提 | ⚠️ **必须由你确认**(见 §1):"改写"到什么程度?三种解释对应的工作量差 3 倍 |

---

## 1. ⚠️ 先定歧义:"改写"指哪一种?

这句话可以指三种完全不同的做法,请先选定 —— 它决定后面一切:

| 方案 | 含义 | 工作量 | 结果归属 |
| --- | --- | --- | --- |
| **A. 复制 + 裁剪** | 把需要的文件**搬进**本项目,删掉用不到的部分,保留版权头 | **小**(1~2 天) | 仍是衍生作品,须保留 Apache-2.0 归属 |
| **B. 参考重写** | 只读它理解算法,**自己重写**实现 | **很大**(数周) | 完全自有,无归属义务 |
| **C. 复制 + 深度改造** | 搬进来后按本项目风格大幅重构(API/错误/日志/测试全改) | **中**(3~5 天) | 衍生作品,同上 |

> **我的建议是 A**(理由见 §6),但先看数据。

## 3. 一个必须先讲清的事实:裁剪**不解决**根本问题

如果你期望"改写后代码量大幅下降",**数据不支持这个预期**:

| 您可能期望 | 实测 |
| --- | --- |
| 只用 20 行 API → 代码量应该很小 | ❌ 编译要 41 文件 / 9,230 行;OCR 算法本身就有这个体量 |
| 其中 `det/postprocess/mod.rs` 一个文件 | **2,441 行生产代码**(DB 后处理 + unclip),**不可裁** |

**为什么它这么大**:该文件同时维护了**两套多边形偏移实现**
(`unclip_polygon_pyclipper_into` / `unclip_polygon_like_opencv_db`)
与**两套 box_score**(`_pure` / `_opencv`)—— 为了在没有 OpenCV 时也能工作。
我们只用其中一套,理论上可再砍一半,但**需要逐行判断哪个分支是活跃路径**(风险较高,建议留到第二阶段)。

## 4. 三种落地方式的详细对比

### 方案 A · 复制 + 裁剪(建议)

**做法**:
```
core/nbcore/src/ocr/rapid/        ← 新目录(与现有 rapid.rs 同级)
  mod.rs           引擎入口(现 rapid.rs 的封装逻辑)
  det/             3,068 行
  rec/             1,188 行(去掉 word_boxes)
  cls/               492 行
  runtime/           594 行
  vision/          1,217 行
  pipeline/        1,380 行
  config/error/types/lib 等  1,291 行
  ATTRIBUTION.md   ← 版权归属说明(必须)
```

**改动点**:
1. 删掉 6 个不需要的模块,逐个验证编译(`2,402` 行);
2. 把 `snow-memory` 的用法替换为普通 `Vec<u8>`(**它只是为大缓冲做了 OS 页管理**,我们不需要该特性 → 可再删一个依赖);
3. 错误类型并入 `AppError`(现在是独立的 `RapidOcrError`);
4. 日志改走本项目 `tracing`/`log`;
5. 保留 Apache-2.0 归属(`ATTRIBUTION.md` + 文件头)。

| 优点 | 缺点 |
| --- | --- |
| 工作量小(1~2 天) | **仍是衍生作品**,须保留归属 |
| 风险最低(算法原样,不引入新 bug) | 上游更新无法直接合并(但我们也不需要) |
| 可立即消除 `thirdparty/` 的"外部依赖"形态 | 砍掉 20% 后仍有 9,230 行 |

### 方案 B · 参考重写

**做法**:只读它理解算法,自己实现。

| 优点 | 缺点 |
| --- | --- |
| 完全自有,无归属义务 | **数周工作量**,且最大风险是**算法细节丢失** |
| 可只实现真正需要的路径(理论最少) | 质量风险:该 crate 的 DB 后处理与 pyclipper 语义对齐是**调过的**(注释里多处记录踩坑) |

⚠️ **风险提示**:我们已实测发现 RapidOCR(Rust)与官方 CLI 的**检出框几何不同**(§11.7.7),
根因就是 `geo-clipper` 与 `clipper.cpp` 的实现差异。重写如果换算法库,**会重蹈这个坑**。

### 方案 C · 复制 + 深度改造

在 A 之上再统一风格(API 命名、错误、注释、测试)。

| 优点 | 缺点 |
| --- | --- |
| 代码风格统一,后续维护友好 | 收益主要在"观感",**不改变算法与风险面** |
| | 3~5 天,且改动面大 → 回归风险高于 A |

## 5. 三者对比一览

| 维度 | A 复制+裁剪 | B 参考重写 | C 复制+深改 |
| --- | --- | --- | --- |
| 工作量 | **1~2 天** | 数周 | 3~5 天 |
| 落地行数 | ~9,230 | 理论最少(未知) | ~9,230 |
| 归属义务 | 须保留 Apache-2.0 | **无** | 须保留 |
| 算法风险 | **最低**(原样) | **最高**(重实现) | 低 |
| 消除外部依赖形态 | ✅ | ✅ | ✅ |
| 推荐 | ✅ **建议** | ⚠️ 除非有法务要求 | 可选后续 |

## 6. 我的建议与理由

**建议:方案 A(复制 + 裁剪),分两阶段:**

**第一阶段(建议立即做)**:
1. 把需要的 9,230 行搬进 `core/nbcore/src/ocr/rapid/`;
2. 删掉 6 个不需要的模块;
3. 去掉 `snow-memory` 依赖(换 `Vec<u8>`);
4. 保留 `ATTRIBUTION.md`;
5. 验证:`cargo test` 全绿 + **端到端识别结果与现在逐字一致**。

**理由**:
- ✅ **消除的是真正的痛点** —— 你现在要的是"不再以第三方库形态存在",A 完全达成;
- ✅ **风险最低** —— 算法一行不动,已修的 arena 缺陷、已验证的输出一致性全部保留;
- ✅ **成本可控** —— 1~2 天 vs 数周;
- ⚠️ **归属义务本就存在**:即便不改写,我们现在也在分发 Apache-2.0 代码。
  方案 A **不新增**任何法律风险 —— 该带的 `LICENSE`/`COPYRIGHT` 现在也必须带。

**第二阶段(可选,以后再做)**:
进一步精简 `det/postprocess/mod.rs`(2,441 行里有一套 OpenCV 分支我们不用)——
**但需先确认哪套是活跃路径**,建议等有完整质量回归基线后再动。

## 12.3 过程中遇到并解决的四个问题

| # | 问题 | 处理 |
| --- | --- | --- |
| 1 | **edition 差异**:上游是 2024,本项目是 2021 → 3 处 `let`-chain 语法不合法 | 改写为嵌套 `if`(2 处),1 处随 `turbojpeg` 特性删除 |
| 2 | **`snow-memory` 依赖**:`RasterBuffer` 4 处使用 | 换 `Vec<u8>` —— 调用点(`len`/`into_vec`/`chunks_exact_mut`)全部由 `Vec` 原生提供,**等价替换** |
| 3 | **命名空间冲突**:引擎的 `Result` 是单泛型别名,门面里 `OnceLock<Result<(), String>>` 解析错 | 显式写 `std::result::Result` |
| 4 | **`cfg(feature)` 失效**:168 个警告中 **141 个**是 `unexpected cfg condition value` | 在 `Cargo.toml` 声明这 9 个特性为**空特性**(语义:固定不启用),警告归零 |
