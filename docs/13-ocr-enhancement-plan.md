# 14. 用户选项设计:档位与内存的关系(含实测)

> 回应:设置项「识别偏好」「引擎驻留」是否纳入内存优化。
> **结论:纳入,但各档位的内存差异必须先实测** —— 否则会设计出"伪选项"。
> 本节全部数据为实测(docs/12 §7/§8 + 本节实验),非估计。

## 14.1 先泼冷水:各旋钮的实测差异

| 旋钮 | 内存差异 | 耗时差异 | 质量差异 | 是否值得暴露 |
| --- | --- | --- | --- | --- |
| 关 ORT mem pattern | **-43~52M** | **4 倍**(screen 4.1→18.2s) | 无 | ❌ 代价不可接受 |
| 优化级别 L3→L1 | **-19~28M** | 持平 | **指纹不变** | ❌ 白捡,直接做(已做,docs §8) |
| det 放大上界(档位) | 见 §14.2 | 随档位降 | 小图不变/宽扁图变 | ✅ 可暴露 |
| session 驻留 | 稳态 40M vs 0 | 重建 ~250ms | 无 | ✅ 可暴露 |
| rec_batch_num / 线程数 | ~0 | — | — | ❌ 无差异,不暴露 |

> 💡 **关键**:全屏截图(最常见场景)的 det 输入 1312×736,在**任何档位下都低于全部上限**
> —— 所以「识别偏好」**不影响全屏场景的内存**(实测 196/198/197M 三档几乎一致)。
> 它只影响**小图/宽扁图**。这一点必须在 UI 上说清楚,否则用户会误以为它能压全屏内存。

## 14.2 「识别偏好」三档实测(docs §7 基础上补测)

| 样例 | 质量(3.0/2560) | 均衡(2.0/2048) | 内存(1.5/1600) |
| --- | --- | --- | --- |
| mixed14 峰值 | 215.4 M | **115.7 M** | **82.1 M** |
| code12 峰值 | 234.5 M | 127.7 M | **90.4 M** |
| screen 峰值 | 196.0 M | 198.2 M | 197.0 M(不变) |
| crop1920x600 峰值 | 311.3 M | 208.9 M | **140.6 M** |
| **mixed14 指纹** | 6e9e21d4 | **相同** | **相同** |
| **screen 指纹** | 043fb1fe | **相同** | **相同** |
| code12 指纹 | 85d17d5a | 变(改善方向) | 变 |
| crop1920x600 指纹 | ae2a2fbc(82 行) | 变(83 行) | 变(88 行) |

**解读:**

- **小图(mixed14)**:三档结果逐字相同,内存 215→116→82M —— 收益最大、零代价;
- **全屏(screen)**:三档结果与内存都几乎不变 —— 该档位管不到它;
- **宽扁图(crop1920x600)**:内存大降(311→141M),但行数 82→83→88,**质量有变化**,需用户知情;
- **code12**:随档位变化,方向与 docs §7 一致(少放大→括号/空格更准)。

## 14.3 设计:两个设置项

### ① 识别偏好 `ocrProfile`(枚举,默认 `balanced`)

| 档位 | 内部值 | 映射 | UI 文案(一句话说清代价) |
| --- | --- | --- | --- |
| 质量优先 | `quality` | upscale 3.0 / side 2560 | 小字最准,内存占用最高 |
| 均衡(默认) | `balanced` | upscale 2.0 / side 2048 | 速度与内存均衡 |
| 内存优先 | `compact` | upscale 1.5 / side 1600 | 最省内存,密集小字界面可能漏行 |

- 单一事实源:`pub mod ocr_profile { const QUALITY/BALANCED/COMPACT; is_supported(); to_caps() }`,
  完全复刻 `ocr_backend` 模式(settings.rs:904,含 validate + 迁移修复 + 交叉单测);
- `rapid.rs` 的 `DET_MAX_UPSCALE/DET_MAX_INPUT_SIDE` 从 const 变为**按档位查表**;
- ⚠️ 默认档需要拍板:维持 `balanced`(= 2.0/2048)意味着**当前行为会变**
  (当前 = quality 档)。若要保持现状,默认应是 `quality`。

### ② 引擎驻留 `ocrSessionMode`(枚举,默认 `idle60`)

| 档位 | 内部值 | 映射 | UI 文案 |
| --- | --- | --- | --- |
| 常驻 | `resident` | 不销毁 | 识别最快,后台常驻约 40MB |
| 空闲销毁(默认) | `idle60` | IDLE_TTL=60s(现状) | 空闲 1 分钟后释放内存 |
| 用完即销毁 | `ephemeral` | 识别完立刻释放 | 最省内存,每次识别多等约 0.3 秒 |

- 映射到 `IDLE_TTL`:resident = 永不 / idle60 = 60s / ephemeral = 0;
- `ephemeral` 在 `with_engine` 末尾直接 `release_session()`(已有该函数,复用);
- **此项才是真正影响"后台内存"的开关** —— 识别中的峰值不受它影响。

## 14.4 明确不放进设置的原因(备查)

| 项 | 不暴露的理由 |
| --- | --- |
| mem pattern | 4 倍耗时,没有可接受的档位组合 |
| 优化级别 L1/L3 | 已固定 L1(白捡的 19~28M),无需用户参与 |
| rec_batch_num / 线程数 | 实测内存无差异;线程数只影响速度 |
| int8 量化模型 | 若将来引入,应作为第 4 档并**替换引擎资产**,不是旋钮 |

## 14.5 UI 文案原则

1. 每个选项一句话说清**代价**("可能漏行""多等 0.3 秒"),不只说收益;
2. 在「识别偏好」的说明里写明:**对全屏截图的内存无影响** —— 防止误解;
3. 与现有「文字识别」区(引擎选择)同区摆放,不新开分组;
4. 改档位即时生效:保存设置 → `set_settings` → `release_session()`(该链路已有,复用)。

## 15. rec 模型换档:PP-OCRv4 mobile → PP-OCRv6 small(修复英文词间空格丢失)

> 2026-10。用户报告:截图翻译识别的英文"单词与单词之间没有分割"
> (原文显示为 `Thepublishedpackagecarriesonesnapshotofeverything...`)。

### 15.1 根因(逐层排查后定位)

排查路径:FFI/前端拼装(无嫌疑)→ CTC 解码与字典映射(无嫌疑,`blank + 6623 字 + 空格 = 6625`
与模型输出类数精确匹配)→ rec 预处理宽度策略(与上游一致)→ **模型本身**。

- 用本机模型跑真机冒烟测试复现:同一批裁片里,长行(563×34)空格正常,
  短裁片(184×27、221×25)输出 `Mihomowould` / `betweenthetwo.`,置信度高达 0.99;
- CTC 逐步探针显示:空格类(最后一类)在词隙时间步的最大概率从正常 ~1.0
  **塌到 ~0.3**,输给 blank → 空格被吞。小字号截图(裁片 14~20px 高,
  需放大 2~3.4 倍到 48px)下**整行系统性丢失**;
- 与上游对照:Python rapidocr 3.10 装同款 v4 模型跑同样图片**同样丢空格**
  —— 移植是忠实的,这是 v4 mobile 模型的固有脆弱性;
- 预处理调优不可救药:抗混叠重采样(Lanczos3)、垂直留白(25%)、
  预放大(2×目标高)等手段在**混批宽张量**(生产常态:窄裁片被批内最宽行
  撑到 928~1216px)下顾此失彼,单裁片实验的结论到混批即失效。

### 15.2 方案:仅换 rec 模型,预处理保持与上游一致

| 项 | v4 mobile rec(旧) | v6 small rec(新) |
| --- | --- | --- |
| 英文空格(5 批真机矩阵) | 8 处丢失 | **全部正确** |
| 中文/混排(20px/13px) | 混排丢空格、全角冒号误识 | **全部正确**(还修正了冒号) |
| 60 行全屏推理(4 线程) | 2075 ms | **1569 ms**(-24%) |
| 模型文件 | 10.4 MB | 20.3 MB(+9.9 MB) |
| 字典 | 内嵌 6623 行 | 内嵌 18708 行(`RecSession` 自动读元数据,`ppocr_keys_v1.txt` 仅作兜底存在性检查) |

v6 small 对**未经改动的原始管线**(双线性缩放、混批、det 碎片框)鲁棒,
预处理零改动即满分;det/cls 仍为 v4 mobile(内存加固有效域不变)。

### 15.4 已知瑕疵(未处理,记录备查)

- v4 det 在**特别宽且规整的词隙**上偶发 18×13px 碎片误检框(det_score ~0.66),
  v6 rec 会自信地读出 `11` 之类的噪声(text_score=0.5 拦不住)。v4 时代该框
  同样存在,只是 rec 恰好读出低分内容被过滤。`min_size=3` 的 det 过滤拦不住它,
  提高阈值有召回风险,暂不处理;
- det 会把长行拆成若干碎片框(上游一致),行与行以 `\n` 相接 —— 翻译前文本
  每行是完整的,仅"行内断行"与视觉排版略有差异。
