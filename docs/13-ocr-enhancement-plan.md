## 13.1 问题一:内存还能再省吗?

### 现状分账(实测)

| 项 | 占用 | 依据 |
| --- | --- | --- |
| 引擎 + 模型(常驻) | **~40 MB** | §12 实测建引擎稳态 40.1M |
| ORT 每次推理的内部缓冲 | 未知(**剩余大头**) | 未测 |
| det 输入张量 | 1312×736×3×4 ≈ 11.6 MB | 可算 |
| 150 个裁剪图 + rec 批张量 | 数 MB 量级 | 估算 |

> 峰值地板 ≈ **150 MB**(screen 实测 152M,其中引擎只占 40M)。
> **剩余 ~110 MB 未定位** —— 这是继续优化的前提。

### 候选方案(按预期收益排序)

| # | 方案 | 预期收益 | 成本/风险 |
| --- | --- | --- | --- |
| A1 | **先测再改**:给引擎加分阶段内存探针(§7 用过且有效),把 110M 定位到具体阶段 | 无直接收益,但**决定方向** | 1 次插桩 + 1 次构建 |
| A2 | 关 ORT `mem_pattern`(`with_memory_pattern(false)`) | 可能数十 MB | **需实测**,可能拖慢推理 |
| A3 | PNG 解码直达 BGR,省 RGBA→BGR 整图副本 | ~8 MB(1080p) | 改解码链路 |
| A4 | `rec_batch_num` 6→1 | 小(rec 张量 ~2MB) | 变慢 |
| A5 | int8 量化模型 | 模型/内存大降 | **需验证质量**,新增模型资产 |
| A6 | 识别后立即销毁 session(可配置) | 空闲期省 40M | 每次重建 ~250ms |

> ⚠️ **判断**:地板 150M 里 40M 是引擎、11.6M 是 det 张量,其余大头在 ORT 内部。
> A2/A5 才可能砍它,但都有质量/速度代价。**建议先 A1 拿分账数据再定,避免盲改。**

## 13.2 问题二:把选择权交给用户

### 用户真正能理解的选项(而非内部参数)

| 设置项 | 档位 | 映射到内部 | 默认 |
| --- | --- | --- | --- |
| **识别偏好** | 质量优先 / 均衡 / 内存优先 | `DET_MAX_UPSCALE` 3.0 / 2.0 / 1.5 | 均衡 |
| **引擎驻留** | 常驻 / 空闲销毁(60s) / 用完即销毁 | `IDLE_TTL` / 现状 / 0 | 空闲销毁 |
| **引擎** | 系统内置 / RapidOCR | 已有 | RapidOCR |

### 落地形态

- 设置页「文字识别」区**已有**引擎选择,在此追加两行下拉;
- `settings.rs` 新增 `ocr_profile`(3 档)与 `ocr_session_mode`(3 档),
  走与 `ocr_backend` **完全相同**的模式(单一事实源 `is_supported()` + `validate` + 迁移修复);
- `rapid.rs` 按档位查表取 `DET_MAX_*`(从 const 变为配置)。

> ⚠️ **不建议**直接暴露 `max_candidates`/`rec_batch_num` 这类参数 —— 用户无法理解,
> 出问题没法报障。**每个用户选项必须能翻译成一句人话**。

## 13.3 问题三:文字布局改善(剪贴板一行一行)

### 现状

这是 det 的**框序**(RapidOCR 自带排序),不是**段落序**。问题:
- 同一段落被换行拆开 → 粘贴到文档里碎成多段;
- 中英混排空格规则不统一;
- 多列/表格布局丢失阅读顺序。

### 方案(由轻到重)

| # | 方案 | 做法 | 效果 | 成本 |
| --- | --- | --- | --- | --- |
| B1 | **中文空格规整**(rapid 也接 `normalize_cjk_spaces`) | 复用现成函数 | 中文行内多余空格消失 | **极低** |
| B2 | **段落合并** | 行间距 < 1.5×中位行高 且 缩进相近 → 合段 | 粘贴出来是完整段落 | 中,需 boxes |
| B3 | **英文断词修复** | 行末连字符/单词被切 → 拼接 | 英文跨行不断词 | 低 |
| B4 | **多列/表格重建** | 按框 x 坐标聚类出列,按列序输出 | 表格可读 | 高,易错 |
| B5 | **Markdown 输出** | 标题/列表/表格推断 | 结构化 | 高 |

### 推荐路径

- 第一步:**B1**(零风险,立刻做);
- 第二步:**B2 + B3**(需要 boxes → 与 13.4 共用一次契约改造);
- 暂缓:B4 / B5(场景少,复杂度高)。

> 💡 **关键协同**:B2 要 boxes,13.4 的图上选字**也要** boxes ——
> 「让 recognize 返回 boxes」这件小事是**两个功能的共同前置**,做一次即可。

## 13.4 问题四:在图片中选中文字

### 交互形态(建议)

    [图片预览] ──鼠标拖选──▶ [高亮选中区域] ──Ctrl+C / 右键复制──▶ 剪贴板

### 分级实现(按粒度)

| 级别 | 粒度 | 依赖 | 工作量 |
| --- | --- | --- | --- |
| **S1 行级** | 整行选择(点击选一行,拖选覆盖多行) | 行级 boxes(**已有**) | 中 |
| **S2 字符级** | 精确到字符(像 PDF 阅读器) | **单字坐标 —— 已被裁掉!** | 大 |

### ⚠️ 必须先面对的取舍

S2 需要恢复 `rec/word_boxes.rs`(560 行,方案 A 内化时裁掉,docs/11 §12.2 有记录)。

| | S1 行级 | S2 字符级 |
| --- | --- | --- |
| 用户体验 | 够用(多数场景选一两行) | 最好 |
| 需找回代码 | 否 | **是(560 行)** |
| 内存影响 | 无 | 每行多存 N 个字符框 |
| 建议 | **✅ 先做** | 视 S1 反馈再定 |

### 技术要点(S1)

1. 契约改造:`ocr_entry` 返回 `{ text, lines: [{ text, box: [[x,y]×4] }] }`
   (同时服务 13.3-B2 的段落合并 —— 一次改造两处受益)
2. 持久化:  i) 只存 ocr_text(现状,坐标仅会话内) ← 建议起步
             ii) 新列 ocr_boxes(JSON) → 重开面板可再选字(需迁移 v5)
3. UI:      Image 上叠 Canvas/Repeater 画高亮层;鼠标事件 → 命中检测
   (屏幕坐标 → 图片坐标 → 命中哪个 box → 取对应行文本)
4. 复制:    选中行按阅读序 join,复用 copy_text_to_clipboard

### 宿主已有可复用的基建

| 需求 | 已有 |
| --- | --- |
| 异步识别 | `CoreFacade::ocrEntry`(线程池) |
| 复制到剪贴板 | `copy_text_to_clipboard` |
| 图片显示 | 面板已有图片条目渲染(具体组件待定位) |

## 13.5 建议的实施顺序

| 阶段 | 内容 | 理由 |
| --- | --- | --- |
| **P0** | B1 中文空格规整(rapid 也接 `normalize_cjk_spaces`) | 几行,零风险,立刻见效 |
| **P1** | 契约改造:`ocr_entry` 返回 boxes(行级) | **13.3-B2 与 13.4-S1 的共同前置** |
| **P2** | B2+B3 段落合并 + 英文断词修复 | 用上 P1 的 boxes |
| **P3** | 图上选字 S1(行级) | 用上 P1 的 boxes |
| **P4** | 设置项:识别偏好 + 引擎驻留 | 独立,随时可插 |
| **P5** | A1 内存分账 → 决定 A2/A5 | 需要数据支撑 |

> 💡 **P1 是杠杆点**:一次契约改造,同时解锁段落合并(13.3)与图上选字(13.4)。
