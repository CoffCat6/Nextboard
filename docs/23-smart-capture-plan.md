## 1. 一句话

框选会话建立时**枚举一次**桌面上可截的目标(顶层窗口 + UIA 元素),鼠标移动即
自动框住"光标下的那块",单击采纳;直通模式下单击即确认入库。

**它不改变任何产物语义** —— 截出来的仍是截图,只是"选区从哪来"多了一条路。

---

## 2. 用户拍板的四项(2026-10-26)

| # | 决策 |
| --- | --- |
| 1 | 默认**开启**(设置项 `smartCapture`,缺省 true) |
| 2 | 直通模式(regionAutoConfirm=true)= **单击即确认** |
| 3 | 浮条模式 = 单击**采纳**选区 + 浮出浮条,不自动确认 |
| 4 | UIA 元素级(S3)**做** |

---

## 3. 为什么不放进 CaptureIntent

`CaptureIntent`(capture_session.hpp:38)的语义是"**框完之后去哪儿**":
Region / Fullscreen / Scrolling。智能框选是"**怎么框**",与它正交。

若新增 `CaptureIntent::Smart`,会出现"Smart + 长截图怎么组合"这类无法回答的组合,
且热键/托盘/右键三个入口都要各加一遍。做成 `Region` 会话的内建能力 + 一个设置
开关,入口零改动。

## 4. 架构

### 4.1 数据流

```
startCaptureSession (capture_session.cpp:347)
  ├─ NoteRegistry::hideAllForCapture()          :360   ← 便签先藏(顺带不在枚举结果里)
  ├─ 【新】smart::probeWindows()                候选表(绝对物理像素,z 序)
  ├─ 循环:抓 frozen 底图 → new OverlayWidget(frozen, …, candidates)
  └─ showFullScreen()

遮罩内 (每次 mouseMove,纯矩形运算,无 Win32 调用)
  光标局部逻辑 → hoverStack(pos) → 取层级最高者 → m_candidate → 局部 update
  单击(按下即在候选上 + 位移 < startDragDistance)→ m_selection = m_candidate
  → 走**原有的三出口**
```

### 4.2 枚举时机是硬约束

**必须在任何遮罩 show 之前**。遮罩是全屏置顶窗口,一旦显示出来,`EnumWindows`
的第一条就是它自己 —— 症状是"永远框住整屏"。

位置恰好还在 `hideAllForCapture()` 之后,所以便签也不在候选里。

> 验收 `--smart-live-flow` 专门钉这一条:真走 startCaptureSession、真枚举,
> 断言候选表里**不含遮罩自己的 HWND**。

### 4.3 第四套坐标

遮罩上原本已有三套(capture_session.hpp 头注释):逻辑像素 / 桌面绝对物理 /
选区局部物理。智能框选引入第四套 Win32/UIA 口径,故:

- 产出侧(`smart_capture.cpp`)只吐**绝对物理像素**;
- 换算集中成纯函数 `toLocalLogical(globalPhysical, screenPhysical, dpr)`,可断言;
- 屏幕物理矩形 = **原点取 QScreen(物理)** + **尺寸取底图(必为物理)**。

最后这条是刻意的:QScreen::geometry() 的**宽高是逻辑像素**,直接拿它当物理用
会在 150% 屏上把候选缩小三分之一。

## 5. 三种实现路径的取舍

| | A. 窗口级(Win32) | B. 元素级(UIA) | C. 图像内容检测 |
| --- | --- | --- | --- |
| 粒度 | 顶层窗口 | 按钮/文本块/浏览器区块 | 视觉块,无语义 |
| 耗时 | 整表枚举 **0~1ms**(实测) | 单次 10~350ms(跨进程 COM) | 4K 几十~几百 ms |
| 覆盖率 | 所有桌面窗口 | 依赖目标应用实现 UIA | 任何画面 |
| 误判 | 极低 | 中 | 高 |
| 结论 | **主线** | **可选深化** | 不做 |

**B 的关键难点**:`ElementFromPoint` 走系统命中测试,遮罩全屏置顶后只会返回
遮罩自己。绕法有两条:
- 运行期 `Qt::WindowTransparentForInput` → Qt 会 hide/show 重建窗口,闪烁且丢鼠标状态,**否决**;
- 从窗口句柄出发**自行遍历子树 + 自己算命中** → 采用(见 §7)。

**C 不做**:它引入的不确定性(误框)与"截图工具应当精确"的产品预期冲突。

## 6. S1/S2:窗口级与重叠切换

### 6.1 过滤规则(全部实测驱动)

| 规则 | 依据 |
| --- | --- |
| 剔除本进程窗口(`GetWindowThreadProcessId == self`) | 本项目的托盘/便签/贴图都不该被框 |
| `IsWindowVisible` / `IsIconic` / `DWMWA_CLOAKED` | 最小化与 UWP 幽灵窗口屏幕上没有内容 |
| shell 类名黑名单(Progman/WorkerW/Shell_TrayWnd/…) | 框住桌面或任务栏没有意义 |
| 最小边长 **60px** | 实测托盘残片是 24×24(`com.xxx-siw`) |
| 宽高比 **≤ 12** | 实测任务栏变体是 3072×70(43.9)、1920×40(48) |

**刻意不用 `WS_EX_TOOLWINDOW` / `WS_EX_NOACTIVATE` 过滤**:大量正常窗口带这些
标志(含本项目的贴图),按标志过滤会误杀。

边界:优先 `DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)`,它排除 Win10
起那圈**不可见**的 7px 拖拽边框;`GetWindowRect` 仅在 DWM 失败时兜底。

> 实测效果:同一台机器上候选从 **19 条降到 10 条**,剩下的全是真实应用窗口。

### 6.2 重叠切换

滚轮在**同位置重叠的多个候选**之间循环(z 序偏移)。场景:两个窗口叠着,
选下面那个。没有重叠时**不吞滚轮事件**(用户能感觉到"这里滚不动")。

### 6.3 单击 vs 拖动

三条同时成立才算"单击采纳",缺一不可:

1. **按下时**就压在候选上(从空白处按下不算);
2. 抬起时位移 ≤ `QApplication::startDragDistance()`;
3. 抬起点仍在候选内。

只判位移会把"从空白按下、拖 2px"误当采纳 —— 用户明明想手框。

## 7. S3:UIA 元素级

### 7.1 贪心下沉(不用 ElementFromPoint,也不用整树 FindAll)

```
从窗口根节点开始,最多 32 层:
  取当前节点的**直接子元素**
  挑出"包含光标 + 尺寸 ≥ minSize"的那些
  同层多个命中 → 取**面积最小**的(视觉上光标正压着的内容)
  记下它作为 best,继续下沉
  本层没有包含光标的子元素 → 到底了
```

- `visited > maxNodes(3000)` 或 `elapsed > budgetMs(350)` 即停;
- 为什么不用整树 `FindAll`:浏览器整树几万节点,一次就能卡几百毫秒;
- 为什么不用 `ElementFromPoint`:见 §5。

### 7.2 触发时机

鼠标停稳 **400ms** 才投(工作线程),在飞时不再投,结果回来还要复核"光标是否
仍停在原处"。取 400ms 的依据:比浮条的 700ms hover tip 短 —— 它是框选的**前置**
动作,不是"想看说明"。

### 7.3 同尺寸容器必须穿透(**实现期发现的缺陷**)

第一版遇到"元素与窗口同尺寸"就 `break`,理由是"再往下也是同一块"。**这是错的**:
实测 Chrome/ZCode 的 UIA 根节点就是一个与窗口等大的容器,真正的内容在它下面。

症状极具迷惑性:功能"看起来接上了",只是**元素级永远等于窗口级**,等于没做。

修复:同尺寸就继续下沉,只是不记为 best;用 `sameSizeStreak > 6` 兜死循环。

### 7.4 真实覆盖率(实测,不美化)

| 目标 | 结果 |
| --- | --- |
| 微信 | ✅ 探到 627×53 的元素(窗口 1050×744) |
| magpie | ✅ 探到 1324×785(窗口 1326×817) |
| Chrome(ZCode / B 站) | ⚠️ `L0` 只有与窗口等大的容器,`L1` 起子节点数为 0 |
| 空标题窗口 | ⚠️ `L0 n=0`,没有可探的树 |

Chrome 的表现是 **Chromium 的惰性无障碍**:未启用无障碍时只暴露最小树。
这不是本实现的缺陷,也不可能靠客户端代码完全绕开(启用完整 UIA 树要么走
`--force-renderer-accessibility`,要么依赖目标进程自己开无障碍)。

**产品含义**:元素级是"锦上添花",窗口级才是保底。设置页的说明文案与代码注释
都不承诺"一定能框到元素"。

### 7.5 层级优先必须按「属主窗口」分组(**两次修正**)

**第一次(2026-10-26 上午)**:候选表是"z 序的窗口 + 追加的元素"两段拼起来的。
元素**永远在窗口之内**,按 z 序取第一个必然拿到窗口 —— 元素级永远用不上。
修法:`candidatesAt()` 按 `level` 降序稳定排序。

**第二次(同日,用户实测反馈后)**:上面那条修法是**错的度量**。
`level` 高不等于"更该被选中" —— **元素属于哪个窗口才是前提**。全屏应用的
UIA 根元素会覆盖整个屏幕,于是"先框到全屏应用,再框另一个非全屏应用就框不出来"。

正确的度量是**所属窗口的 z 序**:

```
排序键 = (该元素属主窗口在候选表里的下标,   // 前台窗口优先
          -level)                            // 同一窗口内部才让元素更细
```

一个元素"在哪一层"由 `windowId` 决定,不是由 `level` 决定。窗口的 z 序取该窗口
在候选表里的位置(枚举顺序)。

**同源修复**:`smartHoverUpdate` 的 `keepElement` 分支(防止异步元素结果被
下一帧鼠标移动覆盖)也必须加条件 —— 只在这个元素**属于当前最前台窗口**时
才保留。否则后台窗口的元素会一直压住前台窗口。

回归断言:`--smart-capture-flow` F 段构造"小窗口 + 后台全屏窗口 + 全屏根元素"
三层,断言悬停小窗口时框住**小窗口**。

### 7.6 层级优先(原始记录)

候选表是"z 序的窗口 + 追加的元素"两段拼起来的。元素**永远在窗口之内**,所以
按 z 序取第一个必然拿到窗口 —— 元素级永远用不上(验收当场翻红)。

修复:`candidatesAt()` 按 `level` **降序稳定排序**(同层保持原 z 序)。稳定排序
是必须的:同层内的 z 序就是"哪个在上面"。

### 7.7 整屏选区下的浮条位置

选中"占满整屏"的候选后,浮条上下都没有空白可站。旧实现夹进窗口内后落在
**正中**(实测 y=4),压住窗口标题栏 —— 而标题栏正是用户确认"框对了没有"的地方。

修法:上下都没有空间时**贴住底边**(留 12px)。取舍理由:截图内容主体通常在上方
(正文从顶部开始),浮条在底部时用户仍能看到标题栏与首屏内容;反过来则一眼全是浮条。

回归断言:F2 段断言整屏选区下浮条`bottom > 屏高 - 60`。

### 7.7b 多屏(2026-10-26 第三轮,用户反馈"多屏下还有问题")

**缺陷 1:离开某屏后预选残留(已修)**

`leaveEvent` 只清了浮条悬停高亮,没清候选。单屏时鼠标永远不会"离开遮罩"
(遮罩就是整屏),所以这条只在多屏出现:光标从 A 屏滑到 B 屏,系统给 A 屏发
Leave、给 B 屏发 Move —— **A 屏上永远挂着那个虚线框**,用户看到两块屏同时"预选"。

修法:`leaveEvent` 里 `smartClearCandidate()` + 停元素探测计时器 +
重置 `m_lastHoverPos`(否则探测结果晚到会把刚清掉的预选画回来)。
只清候选、**不动选区** —— 已采纳的选区是用户的答案。

**缺陷 2:采纳时物理矩形往返换算丢精度(已修)**

候选来自 Win32/UIA,本来就是精确物理像素。旧实现采纳后走
`selectionPhysical()` 重算(物理 → 逻辑四舍五入 → 物理),在 175% 屏上实测
**框住的窗口比窗口本身少 1px**(1086x736 vs 应为 1085x735)。

修法:`selectionPhysical()` 在"逻辑选区仍等于采纳时那个"的情况下直接交回
候选的原始物理矩形(`m_candidatePhysical`);用户一旦拖手柄微调,再走正常换算。

**已用真实数据验证的地基(不是猜测)**

用 Win32 真值(`GetMonitorInfoW` + `GetWindowRect`)与 Qt 假设逐屏对账:

| 屏 | Win32 显示器矩形 | 遮罩窗口矩形 | Qt 几何原点 | Qt DPR |
| --- | --- | --- | --- | --- |
| TL160MDMP03-0 | 0,0 3072x1920 | **一致** | 0,0 **一致** | 1.75 |
| S24 PRO | 3072,-1087 1080x1920 | **一致** | 3072,-1087 **一致** | 1 |
| Mi Monitor | 1150,-1080 1920x1080 | **一致** | 1150,-1080 **一致** | 1 |

`QScreen::geometry().topLeft() == Win32 物理原点` 这条假设在本机**成立**,
且已固化成断言(含"遮罩窗口矩形 == 显示器物理矩形"),将来换了 175% 屏
放在非原点位置时若假设破裂,会立刻翻红。

### 7.8 z 序可靠性(已验证,不是问题)

曾怀疑 `EnumWindows` 的枚举顺序不等于 z 序(那会让"悬停 A 却框住 B")。
用 `WindowFromPoint` 做系统真值交叉验证:**10/10 一致**。这一条已固化成
`--smart-live-flow` 的断言,将来换枚举方式时会立刻暴露。

> 顺带修掉了验收自身的一个缺陷:多屏机器上"每屏一块遮罩",只检查第一块会把
> 别的屏上的候选误判成"不在本屏/被遮挡"。现在按屏分组验证。

## 11. 已知限制

1. **Chrome/Chromium 系列元素级不生效**(§7.4)。窗口级正常。
2. **UIA 探测是跨进程 COM**:目标进程无响应时最坏等满 350ms 预算;它在工作线程,
   不阻塞 UI,但会让"元素框"迟到。
3. **不支持"框住任务栏上的单个图标"** —— 被 §6.1 的碎片过滤挡掉了。
4. **候选表在会话内不变**:会话期间窗口移动/新开窗口不会被感知(遮罩已冻结底图,
   底图本身也过期了,这是既有性质)。
5. **跨屏窗口**:每块遮罩只显示与自己相交的那部分(裁剪),不新增设置项。

## 12. 排障入口

| 现象 | 先看 |
| --- | --- |
| 永远框住整屏 | 候选表是否为空?枚举时机是否跑到遮罩 show 之后(`--smart-live-flow`) |
| 悬停没反应 | 设置项 `smartCapture` 是否被关;光标是否落在 §10 的互斥状态里 |
| 元素级不生效 | 跑 `--smart-uia-flow` 看树结构:是 `L1 n=0`(目标不给树)还是我们停早了 |
| 框住的位置偏 | 首个怀疑对象是 `toLocalLogical` 的换算口径(`--smart-capture-flow` A 段) |
