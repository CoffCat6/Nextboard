# 12 · OCR 峰值内存分析与优化方案

| 项 | 内容 |
| --- | --- |
| 现象 | 识别后峰值内存偏高(用户实测 800+MB) |
| 结论 | **主因是 det 的 `limit_type="min"` 会把图像短边无上界地撑到 736**,属上游为**文档扫描件**设计的默认值,对**截图**是净损失 |
| 性质 | 分析 + 方案,**未改动生产配置** |

## 1. 现象与反直觉的测量结果

用采样线程(每 1~2ms)测**真实峰值**(而非识别后的稳态值),发现峰值**与图像大小无关**:

| 图像 | 像素 | det 峰值增量 |
| --- | --- | --- |
| 32×32 | 1 K | 69 MB |
| 96×32 | 3 K | 201 MB |
| **320×64** | **20 K** | **334 MB** ← 最大 |
| 720×70 | 50 K | 266 MB |
| 1280×720 | 921 K | 125 MB |
| 1920×1080 | 2.1 M | 124 MB |
| **3840×2160** | **8.3 M** | **120 MB** ← 最小 |

⚠️ **8.3M 像素的大图,峰值反而只有 20K 小图的 1/3。** 这说明峰值不由图像大小决定。

## 2. 根因:三层叠加

### 2.1 第一层(主因):`limit_type = "min"` 无上界放大

上游 `DetectorConfig::default()`(`det/detector.rs:59-60`):

```rust
limit_side_len: 736,
limit_type: "min".to_string(),   // ← 语义:把"短边"撑到 736
```

`resolve_limit_side_len_like_python()`(`det/detector.rs:229`)对 `"min"` **直接返回配置值**,
"max" 才走 960/1500/2000 分桶。

**`"min"` 只看短边,不看放大后的总像素** —— 于是:

| 原图 | 短边 | 放大后 | 结果像素 | **放大倍数** |
| --- | --- | --- | --- | --- |
| 720×70 | 70 | → 736 | 7568×736 = **5.57 M** | **110×** |
| 320×64 | 64 | → 736 | 3680×736 = 2.72 M | 134× |
| 8000×120 | 120 | → 736 | **49067×736 = 36 M** | **368×** |

> 📌 这是 PaddleOCR 为**文档扫描件**设计的:扫描件分辨率低,放大能显著提升小字检出率。
> 但**截图的分辨率是屏幕渲染结果**,本就不需要放大 —— 放大只增加内存与耗时。

### 2.2 第二层:`global.max_side_len` 挡不住它

我们已设 `cfg.global.max_side_len = 960`,但那是**第一道** resize(限制最长边);
det 内部**还有第二道** resize,用的是 `det.limit_side_len`。**两者独立,后者会把图重新撑大。**

例:720×70 → 第一道不动(720 < 960)→ 第二道短边撑到 736 → **7568×736**。

### 2.3 第三层:ORT arena 分配器(已修,见 §16)

上游 `enable_cpu_mem_arena` 默认 `true`,实测致 874 MB;关闭后 62 MB。**本轮不重复。**

## 4. 优化方案(按性价比排序)

### ✅ 方案 1:改 `limit_type`(立即可做,配置级)

```rust
// core/nbcore/src/ocr/rapid.rs 的 build_engine()
cfg.det.limit_type = "max".to_string();   // 或保留 "min" 但把 limit_side_len 降到 320~480
```

| 优点 | 缺点 |
| --- | --- |
| 一行改动;小图省 11 倍内存、快 3.3 倍;质量持平或更好 | 全屏场景可能少 4 行(2.7%) |

### ✅ 方案 2:给 det 输入加"放大后上界"(推荐的根本修复)

保留 `"min"` 对小图的收益,但**限制放大后的最长边/总像素**:

```rust
// 概念:min 语义 + 硬上界,避免宽扁图被撑到几十 M 像素
let cap_px = 2_000_000;                       // 例如 ≤200 万像素
let capped_short = ...;                        // 反推允许的短边目标
```

| 优点 | 缺点 |
| --- | --- |
| 兼顾小字检出与内存;长条图不再爆炸 | 需改引擎预处理代码 + 回归测试 |

### 方案 3:长图分区检测

把超长/超宽图(如 8000×120、1000×8000)切成若干块分别检测再合并。
对滚动截图尤其有效。**成本:需处理跨块文本行拼接。**

### 方案 4:收紧框数上限

`det.max_candidates` 默认 **1000**。极端图会产生大量候选框,每个都要 `box_score` + `unclip`。
可降到 200~300。**成本低,但可能漏掉密集小字。**

### 方案 5:调用方按需裁剪(产品级)

现有四条入口中,**框选区域识别**天然比**全屏识别**省内存(前者图像小)。
可引导用户优先框选,或对全屏做智能分区。

### ✅ 已完成的优化

| 项 | 效果 |
| --- | --- |
| 关闭 ORT `enable_cpu_mem_arena` | 874 MB → 62 MB(§16) |
| session 空闲 60s 销毁(D7) | 抑制稳态累积 |
| 显式钉线程数(4) | 避免自动调参取 14 线程 |

## 5. 建议

**立即执行方案 1,但先验证全屏那 4 行差异是否可接受:**

```
若 4 行差异可接受 → 直接改 limit_type = "max"（一行，收益最大）
若不可接受        → 实施方案 2（min + 上界），兼顾两者
```

无论选哪个,**都建议同时在 det 预处理处加一个总像素/最长边上界** ——
因为 `"min"` 语义本身是"无上界放大",任何输入都可能触发爆炸。

## 6. 附:测量方法(可复现)

峰值 ≠ 稳态。本次用**独立采样线程**每 1~2ms 调 `GetProcessMemoryInfo` 取 `PagefileUsage`
(私有提交),记录最大值 —— 才能抓到识别过程中的瞬时峰值。

> 仅测"识别后的值"会完全错过这一现象:720×70 的稳态只有 71 MB,峰值却有 410 MB。

# 7. ✅ 已实施的加固(本节取代 §5 的"建议")

> 目标:**在不改变 OCR 识别结果的前提下,最大化降低峰值内存**。

## 7.1 做了什么

在上游 `limit_type = "min"` 的放大路径上加**两道上闸**(只削减放大,**绝不引入缩小**):

| 闸 | 常量 | 值 | 作用 |
| --- | --- | --- | --- |
| ① 放大倍数 | `DET_MAX_UPSCALE` | **3.0** | 直击根因 —— 上游放大倍数无上界 |
| ② 最长边 | `DET_MAX_INPUT_SIDE` | **2560** | 兜住极端宽高比,保证像素数有硬上界 |

代码位置:

```
core/nbcore/src/ocr/rapid.rs                  常量定义 + build_engine() 应用
core/nbcore/src/ocr/rapid/det/preprocess.rs   compute_resize_hw() 的钳制(核心 3 行)
core/nbcore/src/ocr/rapid/det/detector.rs     DetectorConfig.max_upscale / max_input_side
```

核心逻辑:

```rust
let ratio = if ratio > 1.0 {
    let mut r = ratio;
    if self.max_upscale > 0.0 { r = r.min(self.max_upscale); }
    if self.max_input_side > 0 {
        let longest = h.max(w) as f64;
        r = r.min((self.max_input_side as f64 / longest).max(1.0) as f32);
    }
    r
} else { ratio };
```

## 7.2 为什么是 3.0 倍 / 2560 像素

实测**真实截图**的放大倍数分布,存在一条清晰的鸿沟:

| 图 | 放大倍数 | 放大对识别 |
| --- | --- | --- |
| screen 1920×1080 | 1.36 | ✅ 有收益 |
| crop760 760×420 | 1.75 | ✅ 有收益 |
| wide1920x800(全屏裁切) | 1.84 | ✅ 有收益 |
| crop1920x600(横幅裁切) | 2.45 | ✅ 有收益 |
| **—— 鸿沟 ——** | | |
| **code12 760×80(12px 代码)** | **9.2** | ❌ 有害 |
| **mixed14 720×70(小字)** | **10.5** | ❌ 零收益 |

关键证据:在 **0.4M ~ 5.6M 像素**区间内,mixed14 的识别结果**完全不变** ——
说明那段放大对识别毫无贡献,只是徒增内存与插值伪影。

**为什么不用"总像素上限":** 实测做不到区分 —— 1.2M 就已经让 1920×800 少 7 行、
1920×600 内容改变。因为它把"有收益的中等放大"和"无收益的极端放大"混在一起切。

**为什么不用 `limit_type = "max"`:** 它是"只缩不放",会让小字场景丢失检出,且全屏少 4 行。

**为什么不用只降 `limit_side_len`:** 它同时削弱全屏收益(screen 150→146 行)。

| 样例 | 类型 | 改前峰值 | **改后峰值** | **识别结果** |
| --- | --- | --- | --- | --- |
| screen 1920×1080 | 真实全屏 | 152.4 M | **152.4 M** | **150 行 · 指纹逐字相同** ✅ |
| crop760 760×420 | 真实桌面区域 | 155.2 M | **156.0 M** | **52 行 · 指纹逐字相同** ✅ |
