# 28 · 取消悬停时的分辨率显示,只在实际选定时显示

| 项 | 内容 |
| --- | --- |
| 版本 | v1(2026-11-02) |
| 状态 | **已实施并验收** |
| 关联 | [23-smart-capture-plan.md](./23-smart-capture-plan.md)(智能框选)· [27-smart-capture-latency.md](./27-smart-capture-latency.md)(响应速度) |
| 需求 | 智能框选悬停预览时不要显示分辨率,只在点击确定、浮出工具栏后显示 —— 避免频繁显示导致显示问题 |

---

## 1. 改了什么

`OverlayWidget::drawCandidate()`(候选虚线框的绘制函数)里删掉了 `drawSizeHint()` 调用。

现在只有**一条**路径会画分辨率:已确认的选区(`paintEvent` 的 `if (!sel.isNull())` 分支)。

| 状态 | 虚线框 | 分辨率 |
| --- | --- | --- |
| 智能框选悬停(未采纳) | ✅ 画 | ❌ **不画**(本次改动) |
| 单击采纳 / 拖拽松手(选区定下来 + 浮条浮出) | — | ✅ 画 |
| 手柄微调中 | — | ✅ 画(跟随新尺寸) |

---

## 2. 用户说的"显示问题"是什么:一个真实缺陷

这不是纯审美调整。改动前存在一处**残影**,和用户描述的"频繁显示导致显示问题"完全对得上:

| 环节 | 数值 |
| --- | --- |
| 候选重绘脏区外扩 | **3px**(`smartHoverUpdate` 的 `dirty.adjusted(-3,-3,3,3)`) |
| 尺寸提示底板位置 | 候选**上缘外侧** `sel.y() - h - 4`,约 **22px** |
| 提示内容 | 跟着光标实时变化的 `宽 × 高` |

候选一移动,旧位置的提示底板**落在脏区之外**,Qt 不会重绘那块 —— 屏幕上于是留下一串
"上一处的分辨率数字"。加上悬停时数字每秒变几十次,视觉上就是花屏/闪烁。

> 这就是"只在采纳后显示"能顺带解决的问题:**候选移动时不再有任何需要擦除的
> 浮动文字**,脏区 3px 从此自洽。改动后在 `smartHoverUpdate` 里补了注释,提醒
> 将来若把提示加回候选,**必须**同步把上边扩到 `-26`,否则残影立刻复现。

---

## 3. 顺带发现并修掉的三个既有缺陷

这次改动让 `--smart-capture-flow` 从「5 个预先存在的失败」变成「全绿 48 项」。
过程中暴露出三个**与本次需求无关、但一直在误导人**的问题:

### 3.1 断言描述了一个已不存在的产品行为(5 个失败的真因)

原 B3/G 段断言 `单击即确认,regionConfirmed 已发出`。但 **2026-11-01 起
`regionAutoConfirm` 已删除**,框选恒为浮条模式:单击只**采纳**(选区定下来 +
浮出浮条),确认要用户再点「完成」或按 Enter。代码里 `clickLike` 分支是
`showToolbar(); return;` —— 根本没有 `emit regionConfirmed`。

**这条断言长期是红的,而它红的原因不是代码错。** 留着它会不断误导下一个人去
"修"那段并没有坏的代码。已改为断言当前真实语义:

```
PASS 浮条模式:单击只采纳、不立即确认(regionConfirmed 未发出)
PASS 按 Enter 后 regionConfirmed 发出          ← 投真实 QKeyEvent,走用户同一条路径
```

> 为什么用 Enter 而不是直接调 `confirmSelection()`:后者是 private,为验收方便
> 开后门会让"键盘确认"这条真实链路失去覆盖。

### 3.2 验收自己制造遮挡,把 z 序断言搞红

`--smart-live-flow` 的 z 序交叉验证原本有 4 个不一致,全部形如:

```
我们以为 = "35-主代理与子代理并行方案.md - ..."
系统说   = "Nextboard"
```

"Nextboard" 是**验收进程自己的面板**。验收跑起来时面板可见,`WindowFromPoint`
如实报告"最上层是 Nextboard";而候选表按设计**已过滤本进程 PID** —— 两者当然
不相等。这是验收制造的遮挡,不是产品缺陷。

修法:命中窗口的 PID == 本进程 → 该样本计入 `skipped`(因为"候选表不含自己"
正是被测的**另一条**正确行为,不该反过来惩罚 z 序断言)。

修复后:`一致 6 不一致 0`(原为 `一致 2 不一致 4`)。

### 3.3 元素快照的"写-读回环":光标移到空白处,元素框赖着不走

docs/27 引入快照后,`smartHoverUpdate` 里先算出 `picked`(光标在空白处时为空),
再调 `applySnapshotCandidate()`;而后者通过**副作用**写 `m_candidate`,调用方又
回头读 `m_candidate` 来决定本帧画什么 —— 于是上一帧的元素框被读回来,永远不消失。

`--smart-capture-flow` B2 段(`悬停到空白处预选清空`)抓到了它。

修法:双重保险。

1. `smartHoverUpdate` 只在 `picked` 非空时才查表(空白处不查);
2. `applySnapshotCandidate(cursorLocal, QRect* outLocal)` 显式交出落地的局部矩形,
   调用方**不再**回头读 `m_candidate` —— 消除写-读回环这个结构性问题本身。

## 4. 验收

`--smart-capture-flow` **48 项全绿**(这是该 flow 第一次全绿)。新增/改写的关键断言:

| 断言 | 守的是什么 |
| --- | --- |
| 悬停候选时**不**显示尺寸提示(提示区亮度 157 < 200) | **本次需求的正面断言** |
| 采纳后显示尺寸提示(亮度 167 > 128 且 > 悬停时的 157) | 只在选定时显示 |
| 浮条模式:单击只采纳、不立即确认 | 产品的真实语义(原断言已过时) |
| 按 Enter 后 regionConfirmed 发出 | 确认链路仍然通(走真实键盘事件) |
| 副屏:按 Enter 确认后 regionConfirmed 发出 | 同上,多屏口径 |
| 悬停到空白处预选清空 | 写-读回环回归 |
| EnumWindows 顺序与 WindowFromPoint 一致(不一致 0) | 排除本进程遮挡后的 z 序 |

实测日志节选:

```
SMART-CAPTURE  悬停未采纳:提示区亮度 = 157 (候选不画尺寸提示 → 不应有白板)
SMART-CAPTURE  PASS 悬停候选时**不**显示尺寸提示(提示区亮度 157 < 200)
SMART-CAPTURE  采纳后:提示区亮度 = 167  采纳计数 = 1  候选 = QRect(90,80 300x200)
SMART-CAPTURE  PASS 采纳后显示尺寸提示(亮度 167 > 128 且 > 悬停时的 157)
SMART-CAPTURE  RESULT failures = 0
```

**亮度为什么只差 10?** 白板是 α120 半透明,压在浅底 `0xF2` 上:纯底图经 90α 黑罩
后约 157,叠白板后 167。深色底图上差异会大得多(黑板把底图压暗)。这条断言验的是
"有板 / 没板"这个**布尔差异**,不是对比度大小。

全量回归(9 条 flow)全绿:

```

--smart-live-flow          FAIL=0
--smart-uia-flow           FAIL=0
--smart-settings-flow      FAIL=0
--capture-toolbar-flow     FAIL=0
--editor-flow              FAIL=0

```

> 占用的环境问题,与本次改动无关。

## 5. 需要留意的连带影响

1. **`drawSizeHint` 的注释已更新**:原写"选区与候选预览共用",现已不成立。
2. **`updateForSelectionChange` 的 `-26` 外扩仍然必要**(选区还画提示);
   **`smartHoverUpdate` 的 `-3` 也是对的**(候选不画了)。两处数值不同是**有意**
   的,注释里写清楚了原因,避免下一个人"统一"成同一个值。
3. **拖拽手框也会显示分辨率**。因为松手即产生选区(浮条随之浮出),语义上属于
   "已选定"。若将来要求"只有点浮条按钮才显示",那是另一套逻辑,需要在
   `showToolbar` 上加一个"用户主动确认"的标记。
