## 1. 为什么现在做(价值与时机)

### 1.1 需求侧

滚动长截图(长网页、聊天记录、代码文件、Excel、PDF 连续页)是截图工具的**第一梯队刚需**:
Snipaste 之外的主流截图工具(FastStone、PixPin、微信/QQ 截图、ShareX)全都有,而它恰恰是
「截图 + 素材库」这个产品定位下最能拉开体感差距的一项 —— 长图一旦进库,还能接 OCR 与翻译,
现有链路(入库 → FTS → OCR → 翻译)会立刻增值。

### 1.2 时机:架构已经就位

这是**关键判据**。滚动长截图传统上难在三件事,**本项目全部已具备**:

| 传统难点 | 本项目现状 | 结论 |
| --- | --- | --- |
| 逐帧采集屏幕 | `nb_capture_monitor_matched`(按屏描述配对)+ `nb_capture_crop`(RGBA 通道),已在框选链路跑熟 | ✅ 现成 |
| 一个能「停留并观察」的遮罩 | `OverlayWidget` 已是每屏一块、支持选区保留 + 8 向手柄微调 + 浮条工具栏 | ✅ 现成 |
| 多帧拼接的坐标/DPI 换算 | `overlay_geometry.hpp` 已把「逻辑像素 / 桌面物理像素 / 选区局部物理像素」三套坐标集中成纯函数并有验收断言(`--capture-toolbar-flow`) | ✅ 现成 |
| 拼接后的下游(标注/OCR/贴图/保存/入库) | 浮条已有 5 个出口,全部吃一张 `QImage` | ✅ 现成 |

> 换句话说:**本功能几乎不碰既有链路**,它是往 `OverlayWidget` 里加一个「长截图态」,
> 采集用现成 API,拼接是一段纯函数 Rust 代码,产物复用 `annotatedConfirmed` 那条「已合成图」通道。

### 1.3 与已下线能力的关系

`regionSkipEditor` 与「框选后进编辑器」已下线(docs/17 §18.5),编辑器只保留右键入口。
**长截图不是把编辑器拉回来**,而是浮条上的**第八个按钮**,走同一条「已合成图 → 入库」通道。

## 2. 目标与非目标

### 2.1 目标(v1 范围)

| # | 目标 |
| --- | --- |
| G1 | 框选后,在浮条上点「长截图」进入长截图态:选区固定,屏幕内容随用户滚轮/拖动推进,逐帧采集并纵向拼接 |
| G2 | 支持**两种推进方式**:① 用户自己滚(推荐,画面真实、无合成伪影)② 程序自动滚(无人值守,质量次之) |
| G3 | 拼接结果**自动去除重叠**并给出去重后的长度;失败(重叠不足/场景变化)时明确提示而非静默出错 |
| G4 | 完成后的长图与该次会话的标注一起合成,走**既有**入库 + 写剪贴板链路(条目 `source=capture`) |
| G5 | 单屏内即可完成;**跨屏不支持**(见 §2.2),但多屏机器上任选一屏可用 |
| G6 | 内存有上限:帧缓冲有字节预算,超预算降级(降低采样精度 / 提示用户分段) |

### 2.2 非目标(明确不做,避免范围蔓延)

| # | 不做 | 理由 |
| --- | --- | --- |
| N1 | **跨显示器拼接** | 选区必须落在单屏内。跨屏时各屏 DPI 与色域可能不同,拼接产物无法解释;且多屏拼接在路线图里本就是独立 backlog 项 |
| N2 | 横向(左右)滚动拼接 | 纵向占 95% 场景;横向留 v2.1,算法同构(把轴参数化即可,但交互文案/滚动方向全部要另写) |
| N3 | 网页「自动识别可滚动容器」 | 需要 UI Automation / 浏览器扩展,与「纯截图工具」定位冲突 |
| N4 | 视频/GIF 录制 | 完全不同的技术栈(编码器 + 容器),路线图独立 backlog 项 |
| N5 | 拼接产物「编辑已有多帧」 | 长图是**一次成型**的产物;要精修走入库后的右键「编辑」 |
| N6 | 跨进程保存进度 / 断点续拼 | 会话级功能,周期性不足 |

## 3. 交互设计

### 3.1 入口

浮条现有 7 个按钮(标注/OCR取字/贴图/保存/透明/完成/取消,docs/14 §16.1 后扩)。
「长截图」作为**第 8 个**按钮插在「贴图」之后、「保存」之前:

```
[标注][OCR取字][长截图][贴图][保存][透明]  [完成][取消]
```

> ⚠️ 浮条宽度已从 552 收到 553 才塞进第 7 个按钮(`overlay_geometry.hpp` 的
> `kToolbarButtonWidth = 79`)。加到第 8 个会到 ~632px,在 1366 宽屏上仍可接受,
> 但**必须同步改验收脚本**(`capture_toolbar_flow.cpp` 按 `kToolbarButtons` 均分算点),
> 否则会「点到隔壁按钮」却假通过。

**长截图按钮只在 `regionAutoConfirm=false`(有浮条)时存在** —— 直通模式没有工具栏,
要让长截图在直通模式下可用,唯一办法是给它一个**独立全局热键**(见 §9 待定项 Q3)。

### 3.2 长截图态(fsm)

```
  ┌──────────── 框选态 ────────────┐
  │ 选区可调、浮条可点            │
  └───────────┬───────────────────┘
              │ 点「长截图」
              ▼
  ┌──────────── 长截图态 ─────────────────────────────┐
  │ ① 选区锁定(手柄消失,防误拖)                   │
  │ ② 选区外遮罩加深(引导视线)                     │
  │ ③ 选区右下角浮出小面板:                        │
  │      [开始]  [自动滚动 ▾]  [结束]  [取消]       │
  │ ④ 选区底部显示实时进度:「已拼接 1420 px」       │
  └───────────┬───────────────────────────────────────┘
              │ 点「开始」→ 进入采集推进
              ▼
  ┌──────────── 采集中 ──────────────────────────────┐
  │ 用户滚动页面 / 拖动选区外的滚动条 / 自动滚动中   │
  │ 每帧:检测重叠 → 追加 → 播放「已吸收 N px」反馈   │
  │ [结束] 完成并合成(或重叠不足时给出提示)        │
  └──────────────────────────────────────────────────┘
```

### 3.3 关键交互决策

| # | 决策点 | 选择 | 理由 |
| --- | --- | --- | --- |
| I1 | 选区在长截图态能否调整 | **不能**(锁定) | 选区就是采集窗口;中途改变窗口尺寸会让已采集帧与新帧宽度不一致,拼接必然错位 |
| I2 | 谁来滚 | **优先用户自己滚** | 程序滚动依赖 `SendInput` 发滚轮事件,会与用户操作打架、对「滚动到底」的判定也可能失准;用户自己滚最真实 |
| I3 | 每帧怎么采 | **只采选区矩形**(不是整屏再裁) | 选区物理尺寸已知,直接算裁剪矩形;省一次整屏拷贝(4K 约 33MB/帧) |
| I4 | 何时算「一帧」 | **内容变化即一帧**,不是定频 | 用户滚动才有新内容;定频采样会在未滚动时产生重复帧,白白耗预算 |
| I5 | 重叠检测的粒度 | 选区宽度的**中间 60% 列** | 滚动条/固定侧栏都在两侧边缘;只比中间列可避免「Banner 不动导致误判为未滚动」 |
| I6 | 拼接失败怎么办 | **保留已采部分 + 明确提示** | 静默给出缺行的长图比失败更糟(用户不会发现) |
| I7 | 终止条件 | 用户点「结束」/ Esc / 检测到滚动到尽头 | Esc 语义沿用遮罩全局取消,但**长截图态下 Esc 先退到框选态**而非直接取消(见 §3.4) |

### 3.4 Esc 的分层语义

当前 Esc 一步取消整个会话。长截图态引入第二层:

| 状态 | Esc 行为 |
| --- | --- |
| 框选态 | 取消整个会话(现状不变) |
| **长截图态(未开始)** | 回到框选态(选区与浮条恢复) |
| **长截图态(采集中)** | **结束采集并合成**(不丢弃已采集内容 —— 用户常按 Esc 表示「拍到这儿」) |

> ⚠️ 第三条是刻意的:采集中按 Esc 若直接取消,用户会丢掉几十帧的结果。
> 「丢掉」的显式出口是长截图面板上的「取消」。

## 4. 算法设计(核心)

### 4.1 为什么不能「整屏截 + 纵向硬拼」

用户滚动时页面会**恰好滚动整数像素**吗?不会。滚动常带惯性/弹性/亚像素偏移,
且滚动量与选区高度不相等。所以两帧之间通常**既有重叠又有位移**,必须靠
**重叠匹配算出真实位移**,而不是按「假设滚动了选区高度」硬拼。

### 4.2 位移估计:行指纹 + 串匹配

```
帧 A(已拼接末尾)          帧 B(新帧)
┌──────────────┐          ┌──────────────┐
│ 行 0         │          │ 行 0         │ ← B 的首行 = A 的某行 k
│ 行 1         │          │ 行 1         │
│   ...        │          │   ...        │
│ 行 k   <-----┼----------┤ 行 h_A-k     │ ← 重叠区 = A[k..h_A) == B[0..h_A-k)
│ 行 h_A-1     │          │   ...        │
└──────────────┘          │ 行 h_B-1     │ ← 新增内容
                          └──────────────┘
                     新增长度 = h_B - (h_A - k)
```

**步骤**:

1. **取中间列**:对每帧,只取横向 `[0.2w, 0.8w)` 的列(避开滚动条/固定侧栏)。
2. **行指纹**:每行算一个 64 位指纹。实际取**行均值的低 32 位 + 行内相邻差分的低 32 位**,
   比裸哈希对 JPEG 压缩噪声更鲁棒。
3. **候选位移搜索**:设 A 尾部 `T` 行(建议 `T = min(h_A, 0.5·h_B)`)与 B 头部比对;
   对每个候选 `k`,统计 A 尾部与 B 头部在该位移下**连续相等**的行数。
4. **取最优**:连续相等行数 ≥ `minOverlapRows`(建议 12 行或选区高度的 3%)的最大 `k`
   即为位移;若没有任何候选达标 → **本次匹配失败**。
5. **精修(可选,v2.1)**:对匹配上的一对做灰度 SAD 逐像素微调 ±2 行,消除指纹碰撞。

### 4.3 失败模式与处理

| 失败模式 | 现象 | 处理 |
| --- | --- | --- |
| 滚动量 > 选区高度 | 两帧无重叠 | **明确提示**「滚动太快,有内容漏掉」,并在长图上插入**一道 4px 的警示条**(与「疑似漏行」标记同一实现)。不静默补齐 |
| 未滚动 | A 尾部 == B 头部且位移 0 | 丢弃该帧,不占预算 |
| 滚动超过尽头(内容重复) | 两帧完全相同 | 判定为「到达尽头」→ 自动结束采集并提示 |
| 动态内容(视频/动画/广告) | 指纹永远不匹配 | 连续 N 次(建议 3)匹配失败即提示「页面有动态内容,建议关掉自动播放」并结束 |
| 滚动到顶(向上滚) | 位移为负 | v1 **不支持反向上滚续拼**;检测到位移为负 → 提示「已到达起点」 |

### 4.4 拼接与产物

```
结果 = 帧 0 全部  +  Σ(各帧新增部分)
高度上限:MAX_STITCH_HEIGHT = 30000px(超过则停止采集并提示分段)
宽度 = 选区物理宽度(各帧一致,由 I1 保证)
```

> ⚠️ **30000px 上限的依据**:入库走 `ingest_capture_png`(PNG 编码 + base64),
> base64 膨胀 1.33×。6000×30000 RGBA 原始就是 687MB,PNG 压缩后仍可能几十 MB,
> 会撞上 `max_image_mb`(默认 10MB)而被静默丢弃。上限值需在实施时用实测标定 ——
> 见 §7 风险 R3。

### 4.5 算法放在哪一层

| 候选 | 评价 |
| --- | --- |
| **Rust(nbcore)新增 `stitch` 模块** | ✅ **推荐**。纯数据处理,无 GUI 依赖;天然可做**表驱动单测**(与现有 329 个 `#[test]` 同一风格);本项目已有「有逻辑的归 Rust」的明确约定(capture.rs 头注释) |
| C++ 宿主 | ❌ 本仓**没有 C++ 测试设施**(docs/04 §8 D12 已记录过这个结论);像素算法放在没有单测的一侧是明知故犯 |

**FFI 契约建议**(在 ABI v1 上追加,不改既有方法签名):

```
方法: stitch_append
入参:{
  "session": "<uuid>",          // 会话 id,首次调用时由宿主生成
  "rgba_base64": "...",         // 新帧(仅选区矩形),RGBA8
  "width": 1200, "height": 800, // 物理像素
  "reset": false                 // true = 丢弃该会话已有帧(换选区/重新开始)
}
出参:{
  "matched": true,
  "shiftPx": 380,                // 相对上一帧的有效位移(新增内容的像素数)
  "totalHeight": 1420,           // 拼接后总高
  "reason": "ok" | "no-overlap" | "duplicate" | "limit" | "backward"
}

方法: stitch_finish  { "session": "<uuid>" }
  → { "png_base64": "...", "width": 1200, "height": 1420, "gaps": 1 }
方法: stitch_abort   { "session": "<uuid>" }   // 释放会话缓冲
```

> 会话状态放 Rust 侧(进程级 `Mutex<HashMap<String, StitchSession>>`),
> 与 `translate` 的 `HISTORY` 同一套路。宿主只持有 uuid 字符串 —— 无跨语言生命周期问题。

## 5. 实现方案(分阶段)

### S4 · 真实采集与滚动 —— ✅ 已完成 2026-10-17

| 项 | 内容 |
| --- | --- |
| 滚动穿透方案 | **选区挖洞**(`SetWindowRgn` 把选区从窗口区域挖掉),而不是"转发滚轮"。理由见 §7 R2 的更新:转发滚轮等于**盲滚**(用户看到的仍是冻结画面);整窗透明则按钮点不到 |
| 采集节拍 | **定频 500ms + 核心侧去重**。判断"内容变了"本身要先截一帧再比,等于每拍都截;而重复帧由核心按 `duplicate` 丢弃,不占预算。带背压(上一拍未回则跳过) |

## 12. v2 重构(2026-10-21):取消遮罩与挖洞

### 12.1 为什么要推翻 v1 的采集形态

v1 的做法是「全屏半透明遮罩 + `SetWindowRgn` 把选区从窗口区域挖掉」。真机上三个现象说明这条路走不通:

| 现象 | 根因 |
| --- | --- |
| 页面能滚,但长图**只有一屏高** | 窗口区域是**设备像素**,而选区是 Qt **逻辑像素**。150% 缩放屏上洞按 1:1 挖小 → 选区仍被遮罩盖住一部分 → 每帧采到的都是遮罩上的静止画面 → 核心判 `duplicate` → 只吸首帧 |
| 全屏下「开始/结束」面板**看不见、点不到** | 面板退让逻辑在「上下都放不下」时**压进选区底部内侧**,而选区正是被挖掉的那块:画不出来、也点不到 → 点「开始」的点击被下层页面吃掉,采集压根不启动 |
| 选区 = 整屏时功能整体失效 | 「整窗减选区」得到**空区域** = `NULLREGION` → 遮罩与面板一起消失 |

并且「挖洞」与「在选区上画 UI」**本质互斥**:洞里既画不出东西也点不到。四条验收入口当时全绿却挡不住这些,因为没有任何一条断言「面板与洞不相交 / 洞非空 / 非 100% DPI / 整屏选区」。

### 12.2 新形态

采集期**隐藏整个遮罩**,页面完全可见、可交互、可滚动。UI 由 `StitchHud` 承担:

1. **描边窗**:窗口 = 选区**外扩** 2px,描边画在外扩出来那一圈 → 像素天然在抓取区域之外(几何保证,不依赖抓图后端行为);`WS_EX_TRANSPARENT` 鼠标穿透。
2. **面板窗**:「结束」「取消」+ 进度文案。位置由 `overlay::stitchPanelCandidates()` 给出,**硬约束:与选区零相交**;整屏选区时确实无处可放,则允许浮在选区内,靠 `WDA_EXCLUDEFROMCAPTURE` + 分层窗口两道保险。
3. **Esc**:采集期页面持有焦点,本进程收不到 Esc → 用 `RegisterHotKey` 临时注册全局 Esc;注册失败**明确写在面板上**,不静默。

好处:不需要 `SetWindowRgn`、不需要补洞重绘、不需要「逻辑像素↔设备像素」换算窗口区域 —— 整整一类缺陷随代码一起消失。

### 12.3 采集链路:直抓选区

旧链路每帧 = 整屏 BitBlt(4K 约 33MB)→ QImage → `convertToFormat` 深拷贝 → `nb_capture_crop` 再分配一份裁剪图。
新链路 = `nb_capture_monitor_region_matched` → xcap `Monitor::capture_region`,只搬选区(1200×900 约 4.3MB)。

配套:**配对失败硬失败**,删除两处「回退 `captureMonitor(index)`」—— 索引在 Qt 与 xcap 两端口径不同,静默回退等于把 A 屏内容拼进 B 屏长图。

采样间隔因此从 500ms 收到 **150ms**(设置项 `stitchSampleIntervalMs`,80–1000)。

### 12.4 拼接契约:begin/append/finish/abort

```
nb_stitch_begin(session, monitor, region_x, region_y, region_w, region_h, dpr,
                max_height, max_bytes, overlap_ratio, out_err) -> i32
nb_stitch_append(session, rgba, len, width, height, out_result_json) -> i32
nb_stitch_finish(session, out_png, out_png_len, out_meta_json) -> i32
nb_stitch_abort(session) -> i32
```

- `begin` 固化显示器 + 设备像素矩形 + 上限;重复 begin 报错(会话泄漏检测)。
- `append` **逐帧校验帧宽与帧高**;不符即报错(旧实现只查宽度,高度变化会被「看似合理」的位移掩盖)。
- `append` 回传 `debug{k, run, evidence, overlap, threshold, baselineAge}` —— 真机上判断「为什么判 duplicate」不再靠猜。

算法本身**保留**(行指纹 + 连续相等 + 非空白证据行择优,是拿真机数据修正过的),新增三项:

| 新增 | 理由 |
| --- | --- |
| **多基线重试**(保留最近 3 帧指纹) | 一帧动态内容不再让后续全部失配;命中较老基线如实记缺口 |
| **缺口警示条**(4px 橙红,写入结果图) | §4.3 早就承诺「漏行要能被看见」,v1 从未实现。失配后就点结束时在 `finish` 兜底补条 |
| **字节预算**(`stitchMaxBytes`,默认 128MB) | 1200×30000 RGBA 就是 144MB;只按像素限高会让内存先爆。有效上限 = min(像素, 字节/每行) |

## 13. 固定背景图导致拼接失效(2026-10-21 补)

### 13.1 现象与根因

在应用里设置了**个人背景图**之后(DeepSeek Harness 聊天区、pebrel 终端),长截图只会出一屏高,
日志里 21~42 次 `no-overlap`,而用户「实际滚动并不快」。

真机日志给出的决定性数据:

```
长截图: shift=0 total=927 gaps=1 reason="no-overlap" [k=0 run=838 evidence=838 overlap=927]
```

`k=0` 时 **838/927 行逐行相等**(90%):说明背景图**固定在屏幕上**,同一行号两帧像素一致;
而文字在内容坐标里移动,只占约 89 行。

于是「从第 0 行起连续相等」这个前提在数学上不成立:

| 候选位移 | 背景行(≈90%) | 文字行(≈10%) | 结论 |
| --- | --- | --- | --- |
| k=0 | 全匹配 | 不匹配 | run=838,但不是全等 → 判 `no-overlap` 丢弃 |
| k=真实位移 | **全不匹配** | 匹配 | 首行预筛即失败,**永不入选** |

这同时解释了「纯色背景能用、图片背景不能用」:纯色行被 `is_blank()`(判据 `diff≤4 && mean≥740`)
当作空白剔除,不构成假证据;而深色照片背景 mean 远低于 740,不被剔除,于是 90% 的假证据压过真实信号。

### 13.2 解法:行投影互相关

新增 `fingerprint::find_shift_correlation`:把每帧压成一条一维曲线(每行取采样列区间内的
**水平梯度能量**——文字是强边缘,平滑背景边缘很弱),去均值后做归一化互相关取峰值。

关键差别:**允许近似匹配**。逐行精确比较在 10% 内容占比下必然失败,而相关性仍能认出峰值。
背景贡献的常数基线在去均值后相互抵消。

接入方式是**兜底**:`append_frame` 先走原有的逐行比对(纯色/文档场景保持既有行为),
失配时才调用互相关。相关系数低于 `CORR_MIN = 0.75` 视为失败——两张不相关画面不能被硬凑成匹配。

为支持兜底,会话额外保留**上一帧原始像素**(仅一帧,927×724×4 ≈ 2.7MB,相对结果图可忽略)。

确实失败(否则用例无意义),再断言互相关算对。

### 13.4 仍未验证

- **真机回归**:以上是离线构造 + 验收环境,真实 DSH/pebrel 上背景图场景尚未实跑;
- 互相关为 O(H²) 的朴素实现(927 行约 86 万次乘加),在 150ms 节拍内实测可接受,
  但 4K 高选区(2000+ 行)需要改用 FFT 或降低采样行数;
- 固定背景**同时**含大量动态内容(视频/动画)时,相关系数可能被拉低到阈值附近,未覆盖。
