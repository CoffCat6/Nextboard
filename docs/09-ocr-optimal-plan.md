# 09 · Nextboard OCR 增强的最优方案(综合结论)

## 1. 先明确"最优"的判据

OCR 增强不是单一目标,而是**六个约束下的多目标优化**。我按对本项目的重要性排序:

| 优先级 | 判据 | 现状痛点 |
| --- | --- | --- |
| **1** | **质量**:解决内置引擎在"小字号/中英混排/全屏截图"三场景的缺陷 | 全屏场景实测**不可用**(08 §2) |
| **2** | **可落地性**:无 CI 环境下换机可复现,不引入无法维护的黑盒 | 08 §8 已指出第三方 native 依赖是最大风险 |
| **3** | **技术栈一致**:与既有 `nbcore`(Rust)复用构建/FFI/日志/测试 | 宿主 C++ + 核心 Rust 已是双栈,不应再加第三种 |
| **4** | **包体**:守 `<90MB` 红线 | 当前 55.2MB,余量 34.8MB |
| **5** | **感知性能**:交互式"右键识别"不能卡 | 内置引擎小图 48ms;RapidOCR 全屏 3.8s |
| **6** | **内存**:不把峰值推到不可接受 | 08 §10.1 实测瞬时 +95~233MB |

## 2. 候选方案与逐项评分

我评估了五条路线(前四轮陆续浮现):

| # | 方案 | 一句话 |
| --- | --- | --- |
| **A** | C++ `nbocr.dll` + 显式 LoadLibrary | 08 文档原方案(D1) |
| **B** | **Rust 引擎直接嵌入 `nbcore`** | 用 `ort` 在核心内推理,复用既有 FFI |
| **C** | 调官方 CLI 子进程 | 零编译成本 |
| **D** | 常驻 Rust OCR 子进程 + 二进制协议 | `snow-ocr-process` 形态 |
| **E** | Python 包 | 官方安装指南路线 |

### 逐项评分(★=1 分,满分 5)

| 判据 | A C++ DLL | **B Rust 嵌入** | C CLI | D 子进程 | E Python |
| --- | --- | --- | --- | --- | --- |
| 质量 | ★★★★★ | ★★★★★ | ★★★★★ | ★★★★★ | ★★★★★ |
| 可落地性 | ★★ | **★★★★** | ★★★★★ | ★★★ | ★ |
| 技术栈一致 | ★★ | **★★★★★** | ★★ | ★★★★ | ☆ |
| 包体 | ★★★ | **★★★★** | ★★ | ★★ | ✗ |
| 感知性能 | ★★★★ | **★★★★★** | ★★ | ★★★★ | ✗ |
| 内存 | ★★★★ | **★★★★** | ★★ | ★★★★ | ✗ |
| 崩溃隔离 | ★★ | ★★ | ★★★★★ | ★★★★★ | ★★★★★ |

> 因此**真正的差异全在工程属性上**,这正是本结论的重心。

## 3. 为什么是方案 B(Rust 嵌入 nbcore)

### 3.1 决定性理由:08 的 D1 前提已被证伪,而"同栈"价值被低估

08 §1.2 拒绝 Rust 的两条论据(见 [08b §12.2](./08b-rapid-ocr-rs-analysis.md))均不成立:
- "ort 是 rc 版" → 已有生产实现在用 `=2.0.0-rc.13`;
- "无官方 Rust 绑定" → **没有官方包 ≠ 不能自己做**。

而**被 08 完全忽略的成本**是:本项目已经是 **C++ 宿主 + Rust 核心**的双栈。方案 A 会引入**第三种构建体系**(CMake + OpenCV + ORT 静态库 + 手工 patch 上游源码),而方案 B **零新增构建体系**。

### 3.2 五个"零成本复用"——这是我推荐 B 的核心

| # | 复用项 | 方案 A 需付出 | 方案 B |
| --- | --- | --- | --- |
| 1 | **FFI 通道** | 新增 C ABI 6 导出 + 所有权约定(08 §6) | **零** —— 直接走既有 `nb_call` JSON 门面 |
| 2 | **线程模型** | 需处理"不占 `nb_call` 静态锁"(08 §5.2) | **零** —— 就在 `nb_call` 内,天然串行 |
| 3 | **构建链** | 新 CMake 工程 + 剔 main.cpp/JNI + 修 include + 剔 printf 日志 | **零** —— `cargo build --release` |
| 4 | **图像解码** | 需实现 `QImage→BGR8`(注意 bytesPerLine 对齐) | **零** —— `nbcore` 已有 `image 0.25` + `decode_png_to_rgba` |
| 5 | **错误/日志/测试** | 需自建 | **零** —— 复用 `AppError` / tracing / 既有单测框架 |

**关键佐证**:我实测 `nbcore/Cargo.toml` **已经依赖 `image = 0.25`**,与 `rapid-ocr-rs` 的 `image 0.25` **同大版本** —— 依赖树无冲突。

### 3.3 方案 B 的具体形态

```
core/nbcore/src/ocr/
  mod.rs          # 保持现有 recognize_configured 签名不变(对外契约)
  system.rs       # 现有 Windows OCR(platform 模块原样迁入)
  rapid.rs        # 新增:RapidOCR 引擎封装
  dispatch.rs     # 新增:auto 兜底链调度
```

**对外契约零改动** —— `ffi.rs:783` 的 `ocr_entry` 不变,内部按 backend 分派:
- `System` → 现有 Windows OCR;
- `RapidOcr` → 新引擎;
- `Auto` → 先内置,**结果为空或行数 < 阈值时降级 RapidOCR 重试一次**。

**这意味着**:08 阶段 4(T4.4/T4.5)里**最复杂、最易错**的宿主侧三件事——
① `QImage→BGR8` 转换与行对齐;② 不占 `nb_call` 锁的线程编排;③ 60 秒空闲 destroy 的生命周期——
**全部消失**,因为识别就发生在核心进程内、由 `nb_call` 天然串行。

### 3.4 与 D6/D7/D8 三个待拍板项的关系

| 决策 | 方案 A 下的难度 | **方案 B 下的难度** |
| --- | --- | --- |
| **D6 `auto` 兜底链** | 宿主侧要写跨进程降级 + 两组结果拼装 | **核心内一个函数**,且**可写单测** |
| **D7 session 生命周期** | 宿主侧定时器管理 DLL session | 核心内一个 `Session` 结构,可**直接照抄** `snow-ocr-process` 的语义(先 drop 再 load、失败不留旧引擎) |
| **D8 空格补回** | 无差别 | 无差别(建议本轮仍**不做**,理由见 08a §5.3) |

**D7 尤其关键**:08 §10.1 实测"循环识别全屏时涨到 400MB 不回落"。方案 B 里这只是核心内一个 `Option<Engine>` 的 drop —— 而方案 A 里它是"宿主跨 DLL 边界的生命周期管理"。

## 4. 需要诚实面对的代价

我**不打算把方案 B 说得没有缺点**。三个真实代价:

| # | 代价 | 严重度 | 缓解 |
| --- | --- | --- | --- |
| 1 | **`ort` 仍是 rc 版**(`=2.0.0-rc.13`) | 中 | 精确钉版本;`ort` 只在 `ocr/rapid.rs` 内出现,隔离面小;升级是一次性成本 |
| 2 | **包体增加**:ORT 静态链进 `nbcore.dll`(现 4.12MB) | 中高 | 见 §4.1,这是本方案**唯一需要实测把关**的数字 |
| 3 | **OCR 崩溃将影响核心进程** | 中 | `nbcore` 已有 `catch_unwind` + `panic=unwind` 兜底;`ort` 的 native 崩溃无法捕获 → 但**当前 Windows OCR 也在同进程**,风险量级未变 |

### 4.1 关于代价 2 的实测推算(这是本方案的关键风险点)

| 项 | 数值 | 口径 |
| --- | --- | --- |
| 当前 stage | **55.2MB** | 本项目实测 |
| 红线 | <90MB | 08 的 D4 已拍板 |
| 余量 | **34.8MB** | |
| 模型四件 | 15.47MB | 08 实测(硬成本) |
| **留给引擎二进制的余量** | **≈19.3MB** | |

**关键不确定性**:08 §9.4 说的"引擎 16.4MB"是**官方 CLI exe**(含自己的 CRT/启动代码)。
方案 B 是**把 ORT 静态链进已有的 `nbcore.dll`** —— 增量应**显著小于 16.4MB**,因为:
- 不重复 CRT(与 `nbcore` 共用);
- 可裁剪:方案 B 只需 CPU provider,**不需要** CUDA/DirectML/Training 等 ORT 模块。

> ⚠️ **这是必须实测的数字,不能用外推决定**。若静态链 ORT 后 `nbcore.dll` 超过约 34MB(即 stage 破 90MB),则**降级到方案 D**(子进程)。

## 5. 为什么否决/降级其余方案

### 方案 A(C++ `nbocr.dll`):降级为回退
不是不可行,而是**在方案 B 可用时没有理由选它**:
- 需要自研 C ABI(08a §1.2.1 已证明 spike 制品里**根本没有 dll/头文件**);
- 需要打 3 处上游 patch(剔除 main.cpp/JNI、修 include 路径、剔 printf 日志);
- 需要手工处理跨 CRT 所有权(08 §6 硬性约定 1);
- **换来的是"复用上游官方实现"——而这个收益,方案 B 通过 `rapid-ocr-rs` 同样拿到了**。

### 方案 C(CLI):仅作测试工装
08a §11 已详述:每次识别 **+~382ms 无法摊薄**(进程启动+模型重载),输出是**混排文本需脆弱解析**(坐标只能正则解析日志行)。**但它的零成本探路价值极高** —— 见 §6 的 M0。

### 方案 D(常驻子进程):**包体的保险**
质量与崩溃隔离最好,但需自建协议(参照 `PROTOCOL.md`)+ mmap + 生命周期,`snow-ocr-process` 用了 **596 行 service + 75 行协议** 才做到。**仅当方案 B 的包体实测失败时启用**。

### 方案 E(Python):**明确否决
引入 Python 运行时与 12 个依赖包,与本项目"单 exe + app-local CRT"的发布形态根本冲突(08a §10.1)。

## 6. 推荐执行路径

把 08a 的阶段 0–6 按方案 B 重排,**前置一个零成本的 M0 门禁**:

```
M0 ── 零成本探路(1~2 天,不改主干)
     ① 用官方 CLI + 现有模型,在本项目真实样例(桌面截图)上复核质量  ← 08a §11 已备好工装
     ② 【关键】在 core/ 下加一个最小实验 crate,静态链 ORT,实测 nbcore.dll 增量体积
        → 若增量 <= 19MB:走方案 B(主线)
        → 若增量 >  19MB:改走方案 D(子进程)
     ③ 同时用 CLI 跑 v4-mobile / v5-mobile / v6-small 档位对比(改参数即可,无需重编译)
            |
            v
M1 ── 依赖与模型落地(08a 阶段 1)
     · 模型取 08b §12.3 答案1 的直链 + SHA256 + dict_url(已核实过,省去自建基线)
     · 复核 ModelScope v3.6.0/v3.9.1 路径有效性

     · Session 生命周期照抄 snow-ocr-process 语义(先 drop 再 load、失败不留旧引擎)+ 等价单测
     · 模型加载失败 → 持久化负结果并当场回退(08b §12.3 答案5)

     · ocr_probe 接受 backend 参数(向后兼容)
```

## 7. 无论选哪条路,都必须做的事

这些**与路线无关**,是前四轮反复验证的硬约束:

| # | 事项 | 依据 |
| --- | --- | --- |
| 1 | **`ocr_backend` 三处值集合收口为单一来源**(`settings.rs:508-515` / `:898-919` / `ocr.rs:81-89`) | 08a §1.2.3:否则"选了 RapidOCR 实际跑内置引擎",**且测试查不出** |
| 2 | **宿主/核心必须在派发前拦截 `rapidocr` 值** | 同上 —— `Backend::parse` 把未知值归为 `System` 是**有意设计** |
| 3 | **`ocrScale` / `LanguageChoice` 对 RapidOCR 语义分叉要显式处理** | 08a §2.3:不接线 `normalize_cjk_spaces`;设置页按引擎显隐 |
| 4 | **体积文案 5 处 + `package.ps1:161` 阈值常量** | 08a §1.2.4:漏改会每次打包刷 WARN |
| 5 | **`auto` 兜底链必须有显式测试** | 防止"两条路都返回文本、质量回归查不出" |
| 6 | **保留 CLI 作为对照基准工装** | 08a §11.4:验证自研实现与官方输出一致 |

## 8. 最终建议(一句话版)

> **走方案 B:把 RapidOCR 作为 Rust 引擎直接嵌入 `nbcore`,复用既有 `nb_call` FFI,宿主侧零改动;
> 用 M0 的零成本实验先验证包体增量,若超红线则降级到方案 D 子进程形态。**

### 三条最重要的理由
1. **质量收益与路线无关**(模型相同),所以应按**工程成本**选路 —— 方案 B 成本最低;
2. **08 的 D1 前提已被证伪**,而"与既有 Rust 核心同栈"的价值 08 从未计入;
3. **它让 08a 中最难的三件事(图像转换/线程编排/DLL 生命周期)直接消失**。

### 三个必须先做的动作
1. **澄清 `rapid-ocr-rs` 的许可与来源关系**(合规前置);
2. **实测静态链 ORT 后的 `nbcore.dll` 增量**(决定 B 还是 D);
3. **用 CLI 在真实桌面样例上复核质量 + 档位**(零成本,决定用 v4 还是 v6)。
